Takeaways for gfx908 targets:
- Quark runs fine on gfx908 (calibration, export, eval). The blockers are Quark's model templates (no qwen3 AWQ/GPTQ
  config in 0.13; pass a custom `algo_configs` if you need them) and vLLM's Quark loader (no INT4 weight-only scheme).
- For a model you need to *serve* on MI100 today, use GPTQ-format INT4/INT8 from GPTQModel (below). Use Quark INT4 RTN
  only as a quality reference (+5.8% PPL on Qwen3-8B).
- Do not use Quark's static per-tensor `int8` W8A8 on Qwen3-class models: PPL 79 vs 9.7. A per-channel/per-token W8A8
  scheme was not tested.

## Scheme choice for gfx908 (Step 2 plan)

The target is serving on our vLLM fork on MI100, so pick by what we can *run*, not only what Quark can *produce*:

| scheme | quantize on gfx908 | serve on our stack | notes |
|---|---|---|---|
| INT4 weight-only, group 32/128 (e.g. `int4_wo_32`, `int4_wo_128`) | **works** (RTN; AWQ/GPTQ need a custom algo config for qwen3) [measured] | GPTQ-format INT4 serves well (Exllama dual GEMV, our W4A8 paths) [measured]; **Quark-format INT4 does not load in vLLM** [measured] | |
| INT8 weight-only | [unverified] | GPTQ-8bit serves (Exllama 8-bit kernel) [measured] | |
| W8A8 int8 | Quark `int8` (static per-tensor) runs but breaks quality (PPL 79 vs 9.7) [measured]; per-token/per-channel [unverified] | Quark int8 loads in vLLM via TritonInt8ScaledMM [measured]; kernel also exists: aiter CK `module_gemm_a8w8`, per-token fp32 scales, verified on gfx908 (aiter branch `mi100-a8w8-2026-08`); vLLM serving route on gfx908 [unverified] | per-128-block scale layouts gave garbage — use per-token/per-channel |
| FP8 (`fp8`, `ptpc_fp8`), FP8 KV cache | possible as fake-quant | **not deployable**: no FP8 hardware; vLLM FP8 paths are disabled on gfx908 | do not plan these for MI100 targets |
| MXFP4 / MXFP6 / FP4 | as above | **not deployable** | |
| `kv_cache_scheme` | — | use `null` for MI100 targets | |

If the user asks for FP8 "for MI100", say it can't run here and offer INT4/INT8 weight-only.

## Known-good baseline: our GPTQModel recipe (use as the comparison arm)

Our GPTQModel quantization script (GPTQModel 7.3.5, Python 3.13t, transformers 5.16.1, torch 2.10.0+rocm7.0):

- `QuantizeConfig(bits=4, group_size=32, sym=True, desc_act=False, true_sequential=True, lm_head=False, mse=2.0)`.
- Calibration: 2048 samples, batch 1; chat-wrapped only for models whose definition builds inputs with a chat
  template; plain text for Gemma 4.
- Large dense models: `--balanced` (calibration data + dense VRAM balanced across the 4 cards). That needs our
  one-line GPTQModel patch (`gptq_processor.py`: move the keep-mask to the activation device), and on Gemma 4 the
  script switches off `store_full_length_kv` when no layer shares KV (otherwise every calibration sample's K/V stays
  on GPU0 → late OOM).
- Run with `PYTHON_GIL=0 HIP_VISIBLE_DEVICES=0,1,2,3`; `MEM_TRACE=1` adds a 10 s per-GPU memory trace and an OOM snapshot
  (`logs/mem_snapshot_oom.pickle`, read with `torch.cuda.memory` snapshot tools).
- W4-GS32 beat W8 on GSM8K for a 27B model we tested (79.4 vs 74.4) [measured]. Weight precision of shipped artifacts
  is a quality decision: don't requantize to a lower precision just for speed.
- Publishing: boot-proof on the 4xMI100 serve first; never edit a finished quant dir in place (template changes go
  through a `--chat-template` copy).

## Other quantizers on this hardware

- bitsandbytes NF4 on gfx908 **[measured, 2026-10-07]**: one MI100 (`HIP_VISIBLE_DEVICES=2`,
  `gfx908:sramecc+:xnack-`), bitsandbytes 0.50.2 (the PyPI wheel ships `libbitsandbytes_rocm64`/`rocm70.so`), torch
  2.10.0+rocm7.0. `bnb.nn.Linear4bit` 4096x4096 NF4, bf16 compute: forward OK (rel err vs fp32 0.092, normal for NF4
  weights), backward OK with finite grads, 20 forwards on [8,512,4096] = 70 ms. A full QLoRA training run and multi-GPU
  FSDP-QLoRA on gfx908 are [unverified].
- RTN int4 on real tensors had ~10x the error of int8-GS128 [measured]; MXFP4 −24% on the same probe [measured,
  reference only — not deployable here].

## Execution notes (Step 4)

- Check the cards are free first (`rocm-smi --showuse --showmemuse`, `docker ps`): serve and quant jobs often hold all
  four cards; don't stop a live serve without its owner's go-ahead.
- Memory: 32 GB per card. Quark's calibration placement for >30B dense models on 4x32 GB [unverified]; expect the same
  late-layer pressure we saw with GPTQModel and keep an OOM snapshot hook ready.
- Verify the output by booting it on our fork (`--attention-backend TRITON_ATTN`, TP=4) and a logprob/GSM8K gate,
  not only by Quark's own export check.

## Hardware facts (shared across our MI100 skills)

**Fan rule (our chassis; check yours):** the case fans follow GPU0's temperature only. A single-card bench or job runs on **GPU0**, or another job keeps GPU0 continuously loaded; otherwise the fans stay at idle speed and the loaded card reaches 95 °C junction within minutes (2026-10-07: GPU1 alone, GPU0 idle, hit 95 °C at both 200 W and 290 W; that was the fan artifact, not a card limit). For capability numbers, load all four cards at once (most realistic) and log junction for every card.

gfx908 CDNA1, 120 CUs, 32 GB HBM2 per card, 4 cards all-to-all xGMI (1 hop), 200 W cap by policy. No FP8/FP4 units;
bf16 MFMA is half the fp16 rate. on our host rocm-smi GPU0..3 = renderD130, 131, 128, 129 and an NVIDIA card sits at renderD132; never set
both `HIP_VISIBLE_DEVICES` and `ROCR_VISIBLE_DEVICES`.
