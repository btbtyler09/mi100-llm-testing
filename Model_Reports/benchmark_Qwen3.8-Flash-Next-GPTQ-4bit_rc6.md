## Recommendations

- Use c=2 (interactive-optimal by TTFT/TPOT p99; per-user 60.2 tok/s) for interactive UX.
- Cap concurrency for user-facing requests at the observed sweet spot and send overflow to queue, shedding, or lower-priority batch handling rather than admitting it into the interactive pool.
- Maintain separate routing queues/pools for interactive and batch/offline traffic so background work does not move active sessions past c=2 and degrade p99 TTFT or TPOT.
- When a workload must prioritize aggregate throughput over user latency, treat elevated concurrency only as a batch/offline trade-off and require explicit tolerance for worse p99 TTFT/TPOT and slower per-user output.
- Monitor both p99 TTFT and p99 TPOT separately after c=2 to distinguish whether added load first hurts response start or token pacing, then throttle or rebalance that path accordingly.
- Prefer adding additional serving instances over pushing a single instance beyond c=2 for interactive workloads, so more users can receive performance close to the reported 60.2 tok/s baseline.
- Trigger alerts/rebalancing whenever interactive sessions consistently show higher p99 TTFT or TPOT than the c=2 baseline or per-user throughput drifts downward from 60.2 tok/s.
