## Recommendations

- Use c=2 (interactive-optimal by TTFT/TPOT p99; per-user 42.3 tok/s) for interactive UX.
- Keep interactive traffic in a dedicated low-concurrency pool around the reported c=2 optimum, since that point supports the best TTFT/TPOT p99 behavior and the reported 42.3 tok/s per user.
- Separate asynchronous or long-prompt work into a batch/offline pool; for that pool, favor higher concurrency when it improves aggregate throughput, while explicitly accepting worse TTFT/TPOT p99.
- Prevent batch/offline load from sharing an interactive queue, because high concurrency tends to degrade interactive TTFT/TPOT percentiles even if system-wide throughput rises.
- Scale out interactive capacity by adding isolated serving units or pools rather than pushing a single interactive pool far beyond its c=2 latency knee, keeping per-user latency close to the measured optimum.
- Track p99 TTFT, p99 TPOT, and aggregate throughput together; use rising p99 latency at higher concurrency as the signal to reduce interactive load instead of optimizing only total tokens/s.
- Label any deployment tuned for maximum tokens/s as batch/offline-only, since it should not be used when users depend on stable per-user latency near 42.3 tok/s.
