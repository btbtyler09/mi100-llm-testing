## Recommendations

- Use c=4 (interactive-optimal by TTFT/TPOT p99; per-user 41.0 tok/s) for interactive UX.
- Cap interactive admission around the reported c=4 sweet spot, using the derived aggregate interactive rate of 164.0 tok/s for four concurrent users as a planning anchor while monitoring actual p99 TTFT/TPOT against that regime.
- Separate interactive from batch/offline pools; send latency-insensitive jobs to a distinct lane so they cannot consume scheduler headroom that has been shown to matter for interactive tail latency.
- If interactive demand exceeds the verified c=4 per-user responsiveness envelope, shed, defer, or throttle excess requests instead of letting queued prompt time degrade TTFT/TPOT.
- Run batch/offline saturation above c=4 only as a clearly labeled throughput trade-off, because it may raise overall output but lacks the same p99 interactive justification demonstrated at c=4.
- Scale out interactively by adding comparable serving replicas/lanes rather than forcing more concurrent interactive users through the same measured optimum, and use p99 tail metrics—not average throughput alone—as rollback triggers.
