What changed (all env-gated kernel paths, defaults baked into the image): zero-copy PLE gather inside the
cudagraph, int8-dot (W4A8) GEMVs for the MoE experts / shared expert / dense W4 projections, a fused
router GEMV + softmax + top-10 kernel, group-128 int8 weights for the GDN projections and lm_head at
small M, a fused GDN decode glue kernel, and the shared expert folded into the routed-expert GEMVs.
Accuracy gates on this stack: greedy per-token logprob parity vs the rc2 build at the noise floor,
wikitext-2 PPL 3.141 (HF W4 artifact 3.139), GSM8K 500q 97.0% at c=8 and 96.5% (200q) at c=4.

Known costs: the batched-decode tiers (c>=16) are flat-to-slightly-down because M>4 steps rematerialize
the int8 GDN weights (+54 us/layer) and the KV pool is 206k tokens at 0.90 utilization (0.92 OOMs at the
c=64 tier on a batched-prefill transient). Prefill is unoptimized (2.8k tok/s at 2K, 1.3k at 16K) and is
the next target. Reproduce with `scripts/serve_qwen38_flash_next_rc3.sh` (embedded below) and
`BenchAndReport.py --dataset mixed --dataset-path bench_corpus` from inside the container.

## Executive Summary

The qwen38-flash-next benchmark on 4× AMD Instinct MI100 (gfx908) prioritizes interactive responsiveness, identifying c=4 as the recommended concurrency sweet spot with about 40.2 tokens/sec per user and strong tail latency behavior. Peak aggregate throughput reached 336.80 tokens/sec at c=128 during Concurrency Scaling, but this higher-throughput point sacrifices per-user responsiveness and should be treated as a secondary operating point. The result favors keeping interactive deployments near c=4 while using higher concurrency only when overall throughput matters more than low-time-to-first-token and stable token pacing.

## Recommendations

- Use c=4 (interactive-optimal by TTFT/TPOT p99; per-user 40.2 tok/s) for interactive UX.
- Cap admitted interactive concurrency at the measured c=4 point and defer or shed additional interactive requests once that point is reached, because moving beyond it degrades p99 TTFT/TPOT quality even if aggregate throughput increases.
- Keep batch/offline traffic on a separate serving path or priority lane so it does not consume interactive concurrency headroom; if higher concurrency is used there, treat it explicitly as a throughput-versus-p99-latency trade-off.
- Scale interactive capacity by adding parallel instances of the tested c=4-shaped service configuration rather than forcing more simultaneous requests into one already-saturated interactive flow.
- Route or rebalance traffic using p99 TTFT/TPOT behavior rather than peak throughput alone; when p99 measures drift away from the interactive optimum, reduce admitted interactive load before escalating to higher-concurrency modes.
- Separate reported performance into interactive and batch views so deployment decisions remain anchored to observed p99 responsiveness versus aggregate throughput, not blended averages that can mask user-facing latency harm.
