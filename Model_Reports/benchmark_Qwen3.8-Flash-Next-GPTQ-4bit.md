## Recommendations

- Use c=4 (interactive-optimal by TTFT/TPOT p99; per-user 58.0 tok/s) for interactive UX.
- Cap interactive admission at four concurrent in-flight requests; when TTFT or TPOT p99 begins rising above the c=4 baseline, hold queue depth or shed new traffic instead of increasing concurrency.
- Separate latency-sensitive traffic into its own pool fixed at the c=4 regime, so batch/offline pressure cannot push those users above the measured interactive optimum.
- For batch/offline workloads, allow higher concurrency only as a clearly labeled throughput-vs-latency trade-off, since aggregate throughput may improve while per-user tokens/sec and TTFT/TPOT p99 degrade.
- Treat per-user output rate near 58.0 tok/s as the healthy interactive target; if users consistently fall below this level, lower effective concurrency or rebalance load before adding more work.
- Spread the four concurrent interactive requests evenly across the four serving slots so one slot does not create extra queuing delay that harms TTFT/TPOT p99.
- When interactive demand exceeds the sustainable single-pool limit, prioritize keeping accepted requests at c=4 quality and defer extra requests to a separate waiting/batch path rather than expanding the interactive pool beyond the observed optimum.
